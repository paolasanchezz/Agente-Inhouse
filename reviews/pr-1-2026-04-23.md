## 🟡 Importantes (3)

### 1. Contradição interna: 10 arquivos favicon local violam a §11 que este mesmo PR adiciona

- **Arquivos:**
  - `landing-pages/buzzmonitor/conteudo-que-converte/favicon.png` + `favicon.svg`
  - `landing-pages/buzzmonitor/monitoramento-concorrentes-maio-2026/favicon.png` + `favicon.svg`
  - `landing-pages/buzzmonitor/monitoramento-concorrentes-maio-2026-pt/favicon.png` + `favicon.svg`
  - `landing-pages/buzzmonitor/monitoramento-maio-v1/favicon.png` + `favicon.svg`
  - (4 LPs × 2 arquivos = 8)
- **Problema:** o PR **adiciona** em [landing-pages/GUIDELINES.md](landing-pages/GUIDELINES.md) §11 a regra *"Não criar `favicon.png`/`favicon.svg` na pasta da LP. Sempre apontar pro `logo-icon.png` que já existe no brand"* — mas o **mesmo PR** cria exatamente esses arquivos em 4 LPs buzzmonitor. Os HTMLs apontam corretamente pro brand path (`../../brand/buzzmonitor/assets/logos/logo-icon.png`), então os arquivos locais **não são referenciados por nada** — são código morto que conflita com a regra recém-escrita.
- **Por quê:** a inconsistência regra ↔ implementação no mesmo PR confunde quem ler depois (o que vale: a regra ou o exemplo que a quebra?). A LP cxpress/playbook-whatsapp2026 já segue a regra correta (não tem favicon local) — serve de referência.
- **Sugestão:** remover os 10 arquivos favicon.png/favicon.svg das 4 LPs buzzmonitor neste PR mesmo (ou em follow-up curto). O HTML e o brand path já cobrem o caso — os locais são só ruído.

### 2. Título do PR ultrapassa 70 caracteres (padrão `/commit`)

- **Problema:** título tem 75 chars ("Atualizar LPs buzzmonitor/cxpress, brand Cxpress e adicionar skill /commit"). A skill `/commit` na etapa 5.1 documenta *"≤70 caracteres"*.
- **Por quê:** GitHub trunca títulos longos em várias telas (lista de PRs, notificações por email). Convenção do repo é título curto, detalhe no body.
- **Sugestão:** algo como *"Adicionar skill /commit + ajustes brand Cxpress e LPs"* (55 chars) ou *"Atualizar brand Cxpress, LPs e adicionar skill /commit"* (54). O body já tem o resumo completo.

### 3. Escopo muito amplo — 4 domínios no mesmo PR

- **Problema:** o PR combina (a) skill nova `/commit` + bump setup-agencia, (b) brand Cxpress (logos + mascote + BRANDBOOK), (c) LP cxpress/playbook-whatsapp2026 (+78/-79, mudança estética grande), (d) favicons de 4 LPs buzzmonitor + regra GUIDELINES. São iniciativas independentes.
- **Por quê:** revisar 32 arquivos atravessando 4 contextos é mais trabalho e aumenta chance de achado passar despercebido. Bisect fica menos útil se uma das mudanças introduzir regressão — o commit único mistura tudo. Nesta revisão mesmo, o achado #1 só apareceu porque a regra nova (d) ficou perto dos favicons (d) e não do HTML (a-c).
- **Sugestão:** não precisa corrigir neste PR — já está aberto. Pra próximos: tentar split por domínio quando der. A skill `/commit` junta tudo que estiver staged, então a divisão tem que acontecer antes (commits menores, sequenciais, em branches separadas). Este PR específico: aprovar e seguir.

## Contexto adicional

**Skill `/commit` v2.0.0 — análise qualitativa:**
- Frontmatter válido: `name=commit` bate com o diretório, `version=2.0.0` coerente com CHANGELOG, `allowed-tools: Bash, Read, Grep` é o mínimo usado.
- Regras invioláveis bem explícitas logo no topo (nunca main, nunca force, nunca amend, nunca Co-Authored-By). Isso previne o newbie de pedir "commite isso em main pra mim" e o agente concordar.
- Pre-flight checks cobrem os 3 cenários de falha ruidosa (não é repo, rebase/merge em andamento, nada pra commitar). Mensagens de erro orientam ação em vez de fechar sem explicação.
- Detecção de sensíveis por regex no nome (`.env`, `credentials`, `secrets?\.(json|ya?ml)`, `\.pem$`, `id_rsa`, `\.key$`, `[Tt]oken`). Razoável pro escopo deste repo — não captura secret dentro de arquivo lícito, mas isso seria over-engineering pra colaboradores.
- Passo 5 (abrir PR via API) usa `git credential fill` com `GIT_TERMINAL_PROMPT=0` — elegante e robusto. Trata 401/403 oferecendo fallback manual com título/body prontos pra colar. 👍
